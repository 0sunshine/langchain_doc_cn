围绕你的目标来构建 harness。`create_deep_agent` 会给你一个 production-ready foundation：把它连接到你的数据，塑造它的行为，并添加你的 use case 所需的能力。

:::python

```python
from deepagents import create_deep_agent

agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    system_prompt="You are a helpful assistant.",
    tools=[search, fetch_url],
    memory=["./AGENTS.md"],
    skills=["./skills/"],
)
```

| 参数 | 作用 |
|---|---|
| [`model=`](#model) | 使用哪个 model |
| [`system_prompt=`](#system-prompt) | 给 agent 的自定义 instructions |
| [`tools=`](#tools) | agent 可以调用的 domain tools |
| [`memory=`](#memory) | 启动时加载的 AGENTS.md 文件 |
| [`skills=`](#skills) | 用于按需知识加载的 Skills directory |
| [`backend=`](#backends) | Filesystem backend（默认是 StateBackend） |
| [`permissions=`](/oss/deepagents/permissions) | 文件系统的 path-level access control |
| [`subagents=`](#subagents) | 用于 delegated tasks 的 custom subagents |
| [`middleware=`](#middleware) | 要添加到 stack 的额外 middleware |
| [`interrupt_on=`](#human-in-the-loop) | 在 tool calls 之前暂停以等待 human approval |
| [`response_format=`](#structured-output) | Structured output schema |
| [profiles](#profiles) | 作为 reusable bundle 的 per-model defaults |

## System prompt {#system-prompt}

Deep Agents 自带 built-in system prompt。deep agent 的价值来自 SDK 在 model 之上提供的 orchestration layer，包括 planning、virtual-filesystem tools 和 subagents；model 需要知道这些能力存在，以及何时应该使用它们。内置 prompt 会教 agent 如何使用这套 scaffolding，因此你不必在每个项目里重新推导它；可以通过 [profile](/oss/deepagents/profiles#harness-profiles) 或你自己的 `system_prompt=` 来微调，而不是逐字复制它。

当 middleware 添加特殊 tools（例如 filesystem tools）时，它会把这些内容追加到 system prompt。

### Prompt 组装 {#prompt-assembly}

Deep Agents 会从最多四个命名部分构建 system prompt，使调用方提供的 instructions、SDK 内置 agent guidance，以及任何 model-specific [profile](/oss/deepagents/profiles) overrides 能够以可预测的优先级共存。没有这层结构时，针对 Claude 调优的 profile suffix 可能会根据调用顺序覆盖你的 `system_prompt=` 参数，或被它覆盖；命名 slots 让顺序显式且稳定。

实践中，大多数调用方只会遇到两个 slots：`USER`（你的 `system_prompt=`）和 `BASE`（SDK 默认值）。选择带 built-in profile 的 model（目前是 Anthropic 或 OpenAI）会添加 `SUFFIX`。完整的四段 assembly 主要在你编写 custom `HarnessProfile`，或 debug profile 文本为何出现在某处时才相关。

四个命名部分如下（每个都可能不存在）：

| 名称 | 来源 | 说明 |
| --- | --- | --- |
| `USER` | `create_deep_agent` 的 `system_prompt=` 参数 | `str` 或 `SystemMessage`；未设置时省略。 |
| `BASE` | SDK 默认值（`BASE_AGENT_PROMPT`） | 除非被 profile 的 `CUSTOM` 替换，否则始终存在。 |
| `CUSTOM` | [`HarnessProfile.base_system_prompt`](/oss/deepagents/profiles#harness-profiles) | 当匹配 profile 设置它时，会直接替换 `BASE`。 |
| `SUFFIX` | [`HarnessProfile.system_prompt_suffix`](/oss/deepagents/profiles#harness-profiles) | 当匹配 profile 设置它时，会追加到最后。 |

顺序始终是 **`USER` -> (`BASE` 或 `CUSTOM`) -> `SUFFIX`**，并用空行（`\n\n`）连接。由此得到两个不变量：

1. **`USER` 始终在最前面。** 调用方文本会先于任何 SDK 或 profile 内容，因此无论选择哪个 model，persona/instructions 都具有优先级。
2. **`SUFFIX` 始终在最后面。** Profile suffixes 位于最接近 conversation history 的位置，model-tuning guidance 通常在这里最可靠。

组装形态（已设置 = yes，未设置 = no）：

| `system_prompt=` | profile `base_system_prompt` (`CUSTOM`) | profile `system_prompt_suffix` (`SUFFIX`) | 最终组装出的 system prompt |
| --- | :---: | :---: | --- |
| `None` | no | no | `BASE` |
| `None` | no | yes | `BASE` + `SUFFIX` |
| `None` | yes | no | `CUSTOM` |
| `None` | yes | yes | `CUSTOM` + `SUFFIX` |
| `str` | no | no | `USER` + `BASE` |
| `str` | no | yes | `USER` + `BASE` + `SUFFIX` |
| `str` | yes | no | `USER` + `CUSTOM` |
| `str` | yes | yes | `USER` + `CUSTOM` + `SUFFIX` |

示例：built-in profiles（Anthropic、OpenAI）只附带 `system_prompt_suffix`，因此典型调用会落在 `str` + `no` + `yes` 这一行：

```python
agent = create_deep_agent(
    model="anthropic:claude-sonnet-4-6",
    system_prompt="You are a customer-support agent for ACME Corp.",
)
# Final = USER + BASE + SUFFIX
#       = "You are a customer-support agent for ACME Corp."
#         + "\n\n"
#         + BASE_AGENT_PROMPT
#         + "\n\n"
#         + <Claude-specific guidance>
```

<Note>
    传入 `SystemMessage`（而不是字符串）会触发不同的拼接路径：右侧 assembly（`BASE` 或 `CUSTOM`，再加上任何 `SUFFIX`）会作为额外 text content block 追加到该 message 已有的 `content_blocks` 中。逻辑顺序保持不变（调用方 blocks 在前），并且调用方 blocks 上的任何 `cache_control` markers 都会保留，这对放置显式 Anthropic prompt-cache breakpoints 很有用。
</Note>

<AccordionGroup>
    <Accordion title="Subagent prompts" id="subagent-prompts">
        同样的 overlay 规则也适用于声明式 [subagents](/oss/deepagents/subagents)：每个 subagent 会基于**自己的 model**重新执行 profile resolution，然后把解析出的 profile 的 `base_system_prompt` / `system_prompt_suffix` 应用到它自己编写的 `system_prompt` 上。subagent 的 `system_prompt` 扮演 `BASE` 角色；`CUSTOM` 和 `SUFFIX` 来自与 subagent model 匹配的 profile（它可能与 main agent 的 profile 不同）。

        | `spec["system_prompt"]` | profile `base_system_prompt` (`CUSTOM`) | profile `system_prompt_suffix` (`SUFFIX`) | 最终 subagent system prompt |
        | --- | :---: | :---: | --- |
        | authored | no | no | authored |
        | authored | no | yes | authored + `SUFFIX` |
        | authored | yes | no | `CUSTOM` |
        | authored | yes | yes | `CUSTOM` + `SUFFIX` |

        subagents 没有 `USER` segment；spec 中编写的 `system_prompt` 是最接近的类比，并留在 `BASE` slot 中。只提供 `system_prompt_suffix` 的 profile（built-in Anthropic / OpenAI profiles 的常见情况）只会追加到 subagent 作者写的内容后面；设置 `base_system_prompt` 的 profile 会直接*替换*原 authored prompt，因此要谨慎使用这个字段。
    </Accordion>
    <Accordion title="General-purpose subagent prompt" id="general-purpose-subagent-prompt">
        自动添加的 [general-purpose subagent](/oss/deepagents/subagents#the-general-purpose-subagent) 遵循相同的 overlay 规则，但多一层：GP base prompt 的解析顺序是 **`general_purpose_subagent.system_prompt`（如果设置） -> `HarnessProfile.base_system_prompt`（如果设置） -> SDK GP default**。profile suffix 会叠加在最终结果之上。

        这两个 override 字段都可以携带 base-prompt replacement，但它们不能互换。`general_purpose_subagent.system_prompt` 是 GP-specific configuration；`base_system_prompt` 是主要面向 main agent 的 global override。当二者都设置时，**GP-specific intent 会在 GP subagent 中胜出**，因此同时调优这两个字段时，用户不会看到 GP override 被悄悄丢弃：

        ```python
        register_harness_profile(
            "anthropic",
            HarnessProfile(
                base_system_prompt="You are ACME's support orchestrator.",  # main agent
                general_purpose_subagent=GeneralPurposeSubagentProfile(
                    system_prompt="You are a research subagent. Cite sources.",  # GP subagent
                ),
                system_prompt_suffix="Always think step by step.",
            ),
        )
        ```

        | Stack | 最终 system prompt |
        | --- | --- |
        | Main agent | `"You are ACME's support orchestrator." + SUFFIX` |
        | GP subagent | `"You are a research subagent. Cite sources." + SUFFIX` |

        如果未设置 `general_purpose_subagent.system_prompt`，GP subagent 会回退到 `base_system_prompt`（如果设置），最后再回退到 SDK GP default。
    </Accordion>
</AccordionGroup>

## Middleware

Deep Agents 支持任何 [middleware](/oss/langchain/middleware/overview)，包括下面列出的 built-in middleware、LangChain 的 prebuilt middleware、provider-specific middleware，以及你自己编写的 custom middleware。将 middleware 传给 `create_deep_agent` 的 `middleware` 参数即可。

默认情况下，Deep Agents 可以访问以下 middleware：

- @[`TodoListMiddleware`]：跟踪和管理 todo lists，用于组织 agent tasks 和 work
- @[`FilesystemMiddleware`]：处理 file system operations，例如读取、写入和浏览目录
- @[`SubAgentMiddleware`]：生成并协调 subagents，将任务委派给 specialized agents
- @[`SummarizationMiddleware`]：在 conversations 变长时压缩 message history，使其保持在 context limits 内
- @[`AnthropicPromptCachingMiddleware`]：使用 Anthropic models 时自动减少重复 token processing
- @[`PatchToolCallsMiddleware`]：当 tool calls 在收到结果前被 interrupted 或 cancelled 时，自动修复 message history

如果你正在使用 memory、skills 或 human-in-the-loop，还会包含以下 middleware：

- @[`MemoryMiddleware`]：当提供 `memory` 参数时，跨 sessions 持久化并检索 conversation context
- @[`SkillsMiddleware`]：当提供 `skills` 参数时启用 custom skills
- `HumanInTheLoopMiddleware`：当提供 `interruptOn` 参数时，在指定位置暂停以等待 human approval 或 input

### 预构建 middleware {#prebuilt-middleware}

LangChain 暴露了额外的 prebuilt middleware，可让你添加 retries、fallbacks 或 PII detection 等功能。更多信息请参阅 [Prebuilt middleware](/oss/langchain/middleware/built-in)。

## Skills

你可以使用 [skills](/oss/deepagents/overview) 为 deep agent 提供新的 capabilities 和 expertise。
虽然 [tools](/oss/deepagents/customization#tools) 通常覆盖较底层的功能，例如 native file system actions 或 planning，但 skills 可以包含如何完成任务的详细 instructions、reference info，以及 templates 等其他 assets。
这些文件只有在 agent 判断某个 skill 对当前 prompt 有用时才会加载。
这种 progressive disclosure 会减少 agent 在启动时需要考虑的 tokens 和 context。

示例 skills 请参阅 [Deep Agents example skills](https://github.com/langchain-ai/deepagentsjs/tree/main/examples/skills)。

## Profiles

[harness profile](/oss/deepagents/profiles#harness-profiles) 是一组可复用的 per-model configuration bundle，`create_deep_agent` 会在选择匹配 model 时自动应用它。Profiles 适用于你希望行为跟随 model，而不是跟随 call site 的场景，例如为 Claude 的 instruction style 调优的 system prompt suffix、为 GPT 改写过的 tool descriptions，或只对特定 provider 有意义的额外 middleware。

单个 profile 可以包含：custom base system prompt（`base_system_prompt`）、appended suffix（`system_prompt_suffix`）、tool description overrides、要排除的 tools 或 middleware、要注入的 additional middleware，以及对自动添加的 general-purpose subagent 的 edits。

<CustomizationProfilesPy />

关于 registration keys、merge semantics 和 plugin packaging，请参阅 [Profiles](/oss/deepagents/profiles)。一个范围更窄的配套 API [provider profiles](/oss/deepagents/profiles#provider-profiles)，用于为 provider 打包 model-construction arguments（API keys、timeouts、retry settings）。
