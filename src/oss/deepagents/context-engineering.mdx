Context engineering 是指用正确的格式向 deep agent 提供正确的信息和工具，使它能够可靠地完成任务。

Deep agents 可以访问多种 context。
有些来源会在 agent 启动时提供；有些则会在运行时才出现，例如用户输入。
Deep agents 内置了若干机制，用于在长时间运行的 session 中管理 context。

本页概述你的 deep agent 可以访问并管理的不同类型的 context。

<Tip>
刚接触 context engineering？请参阅[概念概览](/oss/concepts/context)，了解不同 context 类型以及各自适合的使用时机。
</Tip>

## Types of context

| Context 类型 | 你可以控制什么 | Scope |
|--------------|------------------|-------|
| **[Input context](#input-context)** | agent 启动时进入 prompt 的内容（system prompt、memory、skills） | 静态内容，每次运行都会应用 |
| **[Runtime context](#runtime-context)** | invoke 时传入的静态配置（用户元数据、API keys、连接等） | 每次运行独立，并传播到 subagents |
| **[Context compression](#context-compression)** | 内置 offloading 和 summarization，让 context 保持在窗口限制内 | 自动执行，在接近限制时触发 |
| **[Context isolation](#context-isolation-with-subagents)** | 使用 subagents 隔离重型工作，只把结果返回给主 agent | 每个 subagent 独立，在委托时发生 |
| **[Long-term memory](#long-term-memory)** | 通过 virtual filesystem 在 threads 之间持久化存储 | 跨对话持久存在 |

### System prompt

你的自定义 system prompt 会被放在内置 system prompt 之前。内置 system prompt 包含 planning、filesystem tools 和 subagents 的使用指南。你可以用它定义 agent 的角色、行为和知识：

:::python
```python
from deepagents import create_deep_agent

agent = create_deep_agent(
    model="google_genai:gemini-3.5-flash",
    system_prompt=(
        "You are a research assistant specializing in scientific literature. "
        "Always cite sources. Use subagents for parallel research on different topics."
    ),
)
```
:::

:::js
```typescript
import { createDeepAgent } from "deepagents";

const agent = await createDeepAgent({
  model: "google_genai:gemini-3.5-flash",
  systemPrompt: `You are a research assistant specializing in scientific literature.
  Always cite sources. Use subagents for parallel research on different topics.`,
});
```
:::

:::python
`system_prompt` 参数是静态的，这意味着它不会随每次 invocation 改变。
在某些场景下，你可能需要动态 prompt：例如告诉模型“你有 admin access”或“你只有 read-only access”，或者从 [long-term memory](#long-term-memory) 注入“User prefers concise responses”这类用户偏好。
如果你的 prompt 依赖 context 或 `runtime.store`，可以使用 `@dynamic_prompt` 构建能够感知 context 的指令。你的 middleware 可以读取 `request.runtime.context` 和 `request.runtime.store`。
添加 [custom middleware](/oss/langchain/middleware) 请参阅 [Customization](/oss/deepagents/customization#middleware)，更多示例请参阅 [LangChain context engineering](/oss/langchain/context-engineering#system-prompt) 指南。

当只有 tools 需要使用 context 或 `runtime.store` 时，你**不需要** middleware；tools 会直接接收 @[ToolRuntime] 对象（包含 `runtime.context` 和 `runtime.store`）。只有当 tools 需要和 system prompt 更新一起打包时，才需要添加 middleware。
:::

:::js
`systemPrompt` 参数是静态的，这意味着它不会随每次 invocation 改变。
在某些场景下，你可能需要动态 prompt：例如告诉模型“你有 admin access”或“你只有 read-only access”，或者从 [long-term memory](#long-term-memory) 注入“User prefers concise responses”这类用户偏好。
如果你的 prompt 依赖 context 或 `runtime.store`，可以使用 `dynamicSystemPromptMiddleware` 构建能够感知 context 的指令。
你的 middleware 可以读取 `request.runtime.context` 和 `request.runtime.store`。
添加 [custom middleware](/oss/langchain/middleware) 请参阅 [Customization](/oss/deepagents/customization#middleware)，更多示例请参阅 [LangChain context engineering](/oss/langchain/context-engineering#system-prompt) 指南。

当只有 tools 需要使用 context 或 `runtime.store` 时，你**不需要** middleware；tools 会直接接收 `runtime` 对象（包含 `runtime.context` 和 `runtime.store`）。只有当 system prompt 本身必须按 request 变化时，才需要添加 middleware。
:::

<Tip>
    如果要为特定 provider 或 model 调整组装后的 system prompt，请使用 [harness profile](/oss/deepagents/profiles#harness-profiles)：`base_system_prompt` 会完全替换 base prompt，`system_prompt_suffix` 会追加到 base prompt 之后。
</Tip>

### Memory

Memory 文件（[`AGENTS.md`](https://agents.md/)）提供持久化 context，并且会**始终加载**到 system prompt 中。可以把 memory 用于项目约定、用户偏好，以及每次对话都应该生效的关键指南：

:::python
```python
agent = create_deep_agent(
    model="google_genai:gemini-3.5-flash",
    memory=["/project/AGENTS.md", "~/.deepagents/preferences.md"],
)
```
:::

:::js
```typescript
const agent = await createDeepAgent({
  model: "google_genai:gemini-3.5-flash",
  memory: ["/project/AGENTS.md", "~/.deepagents/preferences.md"],
});
```
:::

不同于 skills，memory 总是会被注入；这里没有 progressive disclosure。请保持 memory 精简，避免 context 过载；详细 workflow 和特定领域内容应使用 [skills](/oss/deepagents/skills)。配置细节请参阅 [Memory](/oss/deepagents/customization#memory)。

### Skills

Skills 提供**按需加载**的能力。agent 启动时会读取每个 `SKILL.md` 的 frontmatter，然后只在判断 skill 相关时加载完整 skill 内容。这样既能减少 token 使用量，也能提供专门的 workflow：

:::python
```python
agent = create_deep_agent(
    model="google_genai:gemini-3.5-flash",
    skills=["/skills/research/", "/skills/web-search/"],
)
```
:::

:::js
```typescript
const agent = await createDeepAgent({
  model: "google_genai:gemini-3.5-flash",
  skills: ["/skills/research/", "/skills/web-search/"],
});
```
:::

每个 skill 应聚焦于单个 workflow 或 domain；过宽或彼此重叠的 skills 会削弱相关性，并在加载时膨胀 context。在 skill 内部，主内容应保持简洁，把详细参考材料移到 skill 文件中引用的独立文件里。始终相关的约定请放在 [memory](#memory)。关于编写和配置，请参阅 [Skills](/oss/deepagents/skills)。

### Tool prompts

[Tool](/oss/langchain/tools) prompts 是会影响模型如何使用 tools 的说明。所有 tools 都会暴露模型在 prompt 中可见的 metadata，通常包括 schema 和 description。你通过 `tools` 参数传入的 tools，会把这些 tool metadata（schema 和 descriptions）呈现给模型。deep agent 的内置 tools 被打包在 middleware 中，通常也会向 system prompt 添加更多关于这些 tools 的指导。

**Built-in tools** - 添加 harness 能力（planning、filesystem、subagents）的 middleware 会自动向 system prompt 追加 tool-specific instructions，从而形成 tool prompts，说明如何有效使用这些 tools：
- Planning prompt - `write_todos` 的说明，用于维护结构化 task list
- Filesystem prompt - `ls`、`read_file`、`write_file`、`edit_file`、`glob`、`grep` 的文档（使用 sandbox backend 时还包括 `execute`）
- Subagent prompt - 使用 `task` tool 委托工作的指南
- Human-in-the-loop prompt - 在指定 tool calls 处暂停的用法（设置 `interrupt_on` 时）
- Local context prompt - 当前目录和项目信息（仅 CLI）

**Tools you provide** - 通过 `tools` 参数传入的 tools 会把它们的 descriptions（来自 tool schema）发送给模型。你也可以添加 [custom middleware](/oss/langchain/middleware)，由它添加 tools 并追加自己的 system prompt instructions。

对于你提供的 tools，请确保提供清晰的名称、description 和 argument descriptions。这些内容会指导模型判断何时以及如何使用该 tool。请在 description 中包含*何时*使用该 tool，并描述每个 argument 的作用。

:::python
```python
@tool(parse_docstring=True)
def search_orders(
    user_id: str,
    status: str,
    limit: int = 10
) -> str:
    """Search for user orders by status.

    Use this when the user asks about order history or wants to check
    order status. Always filter by the provided status.

    Args:
        user_id: Unique identifier for the user
        status: Order status: 'pending', 'shipped', or 'delivered'
        limit: Maximum number of results to return
    """
    # Implementation here
    ...
```
:::

:::js
```typescript
const searchOrders = tool(
  async ({ userId, status, limit }) => { /* ... */ },
  {
    name: "search_orders",
    description: `Search for user orders by status.

Use this when the user asks about order history or wants to check
order status. Always filter by the provided status.`,
    schema: z.object({
      userId: z.string().describe("Unique identifier for the user"),
      status: z.enum(["pending", "shipped", "delivered"]).describe("Order status to filter by"),
      limit: z.number().default(10).describe("Maximum number of results to return"),
    }),
  }
);
```
:::

<Tip>
    如果要为特定 provider 或 model 覆盖内置 tool 或用户提供 tool 的 description，请使用 [harness profile](/oss/deepagents/profiles#harness-profiles) 中按 tool 名称设置的 `tool_description_overrides`。`excluded_tools` 会把某个 tool 从可见 tool set 中完全移除。
</Tip>

内置能力请参阅 [Harness](/oss/deepagents/harness)，直接传入 tools 请参阅 [Customization](/oss/deepagents/customization#tools)。

### Complete system prompt

deep agent 的 system message，也就是模型在 run 开始时接收的组装后 system prompt，由以下部分组成：

1. 自定义 `system_prompt`（如果提供）
1. [Base agent prompt](https://github.com/langchain-ai/deepagents/blob/e18e9dcd0e6edc72c0a4a5b76ae752c4bc539752/libs/deepagents/deepagents/graph.py#L37)
1. To-do list prompt：说明如何用 to-do lists 进行 planning
1. Memory prompt：`AGENTS.md` + memory 使用指南（仅在提供 `memory` 时）
1. Skills prompt：skills 位置 + 带 frontmatter 信息的 skills 列表 + 用法（仅在提供 skills 时）
1. Virtual filesystem prompt（filesystem + 适用时的 execute tool 文档）
1. Subagent prompt：Task tool 用法
1. 用户提供的 middleware prompts（如果提供 custom middleware）
1. Human-in-the-loop prompt（设置 `interrupt_on` 时）

## Runtime context

Runtime context 是你 invoke agent 时传入的每次运行配置。它不会自动包含在模型 prompt 中；只有当 tool、middleware 或其他逻辑读取它，并把它加入 messages 或 system prompt 时，模型才会看到。Runtime context 适合放用户元数据（IDs、preferences、roles）、API keys、database connections、feature flags，或你的 tools 和 harness 需要的其他值。

:::python
使用 `context_schema` 定义数据形状：可以用 `dataclasses.dataclass` 或 `typing.TypedDict` class。通过传给 `invoke` / `ainvoke` 的 **`context`** argument 传入值。完整细节请参阅 [Runtime](/oss/langchain/runtime) 和 [LangGraph runtime context](/oss/langgraph/graph-api#runtime-context)。

在 tools 内部，从注入的 @[ToolRuntime] 读取 context：

```python
from dataclasses import dataclass

from deepagents import create_deep_agent
from langchain.tools import tool, ToolRuntime

@dataclass
class Context:
    user_id: str
    api_key: str

@tool
def fetch_user_data(query: str, runtime: ToolRuntime[Context]) -> str:
    """Fetch data for the current user."""
    user_id = runtime.context.user_id
    return f"Data for user {user_id}: {query}"

agent = create_deep_agent(
    model="google_genai:gemini-3.5-flash",
    tools=[fetch_user_data],
    context_schema=Context,
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "Get my recent activity"}]},
    context=Context(user_id="user-123", api_key="sk-..."),
)
```
:::

:::js
使用 `contextSchema` 定义数据形状，通常是一个 Zod object schema（例如 `z.object({ ... })`）。通过传给 `invoke` / `ainvoke` 的 options object 中的 **`context`** 字段传入 runtime values。完整细节请参阅 [Runtime](/oss/langchain/runtime) 和 [LangGraph runtime context](/oss/langgraph/graph-api#runtime-context)。

在 tools 内部，从作为 tool handler `runtime` argument 提供的 `ToolRuntime` 实例读取 `runtime.context`：

```typescript
import { createDeepAgent } from "deepagents";
import { tool } from "langchain";
import type { ToolRuntime } from "@langchain/core/tools";
import { z } from "zod";

const contextSchema = z.object({
  userId: z.string(),
  apiKey: z.string(),
});

const fetchUserData = tool(
  async (input, runtime: ToolRuntime<unknown, typeof contextSchema>) => {
    const userId = runtime.context?.userId;
    return `Data for user ${userId}: ${input.query}`;
  },
  {
    name: "fetch_user_data",
    description: "Fetch data for the current user",
    schema: z.object({ query: z.string() }),
  }
);

const agent = await createDeepAgent({
  model: "google_genai:gemini-3.5-flash",
  tools: [fetchUserData],
  contextSchema,
});

const result = await agent.invoke(
  { messages: [{ role: "user", content: "Get my recent activity" }] },
  { context: { userId: "user-123", apiKey: "sk-..." } },
);
```
:::

Runtime context 会**传播到所有 subagents**。当 subagent 运行时，它会接收和 parent 相同的 runtime context。关于每个 subagent 的 context（namespaced keys），请参阅 [Subagents](/oss/deepagents/subagents#context-management)。

## Context compression

长时间运行的任务会产生大型 tool outputs 和很长的 conversation history。
Context compression 会减少 agent working memory 中的信息量，同时保留与任务相关的细节。
以下技术是内置机制，用于确保传给 LLMs 的 context 始终处于 context window limit 内：

<CardGroup cols={2}>
  <Card title="Offloading" icon="file-export" href="#offloading">
    大型 tool inputs 和 results 会存入 filesystem，并被引用替代。
  </Card>
  <Card title="Summarization" icon="article" href="#summarization">
    接近限制时，旧 messages 会被压缩成 LLM 生成的 summary。
  </Card>
</CardGroup>

### Offloading

Deep Agents 使用[内置 filesystem tools](/oss/deepagents/harness#virtual-filesystem-access) 自动 offload 内容，并在需要时搜索和取回这些 offloaded content。
当 tool call inputs 或 results 超过 token 阈值（默认 20,000）时，会发生 content offloading：

1. **Tool call inputs 超过 20,000 tokens**：文件写入和编辑操作会在 agent 的 conversation history 中留下包含完整文件内容的 tool calls。
    由于这些内容已经持久化到 filesystem，通常是冗余的。
    当 session context 超过模型可用窗口的 85% 时，deep agents 会截断较早的 tool calls，用指向磁盘文件的 pointer 替换它们，从而减少 active context 的大小。

    ![An example of offloading showing a large input which is saved to disk and the truncated version is used for the tool call](/oss/images/deepagents/offloading-inputs.png)

2. **Tool call results 超过 20,000 tokens**：发生这种情况时，deep agent 会把 response offload 到配置的 backend，并用 file path reference 和前 10 行 preview 取代它。Agents 之后可以按需重新读取或搜索这些内容。

    ![An example of offloading showing a large tool response that is replaced with a message about the location of the offloaded results and the first 10 lines of the result](/oss/images/deepagents/offloading-results.png)

### Summarization

:::js
<Note>
当前 summarization 行为（通过 `wrapModelCall` 进行 in-model summarization、准确 token counting，以及自动 `ContextOverflowError` fallback）需要 `deepagents>=1.6.0`。
</Note>
:::

当 context size 超过模型的 context window limit（例如达到 `max_input_tokens` 的 85%），并且没有更多 context 可以 offload 时，deep agent 会 summarise message history。

这个过程包含两个部分：

- **In-context summary**：LLM 会生成 conversation 的结构化 summary，包括 session intent、已创建的 artifacts 和 next steps；该 summary 会替代 agent working memory 中的完整 conversation history。
- **Filesystem preservation**：完整的原始 conversation messages 会被写入 filesystem，作为 canonical record。

这种双轨方式确保 agent 能通过 summary 保持对目标和进度的感知，同时在需要时仍可通过 filesystem search 恢复具体细节。

![An example of summarization showing an agent's conversation history, where several steps get compacted](/oss/images/deepagents/summarization.png)

**Configuration:**
- 在达到其 [model profile](/oss/langchain/models#model-profiles) 中 `max_input_tokens` 的 85% 时触发
- 保留 10% tokens 作为 recent context
- 如果 model profile 不可用，则 fallback 到 170,000-token trigger / 保留 6 条 messages
- 如果任何 model call 抛出标准 @[ContextOverflowError]，deep agent 会立即 fallback 到 summarization，并用 summary + recent preserved messages 重试
- 较旧 messages 会由模型 summarise

:::python
<Tip>
agent 的 [Streaming tokens](/oss/deepagents/streaming#llm-tokens) 通常会包含 summarization 步骤生成的 tokens。你可以使用它们关联的 metadata 过滤掉这些 tokens：
```python
for chunk in agent.stream(
    {"messages": [...]},
    stream_mode="messages",
    version="v2",
):
    token, metadata = chunk["data"]
    if metadata.get("lc_source") == "summarization":  # [!code highlight]
        continue
    else:
        ...
```
</Tip>
:::

:::js
<Tip>
agent 的 [Streaming tokens](/oss/deepagents/streaming#llm-tokens) 通常会包含 summarization 步骤生成的 tokens。你可以使用它们关联的 metadata 过滤掉这些 tokens：
```typescript
for await (const [namespace, chunk] of await agent.stream(
  { messages: [...] },
  { streamMode: "messages" },
)) {
  const [message, metadata] = chunk;
  if (metadata?.lcSource === "summarization") {  // [!code highlight]
    continue;
  } else {
    ...
  }
}
```
</Tip>
:::

:::python
##### Summarization Tool

Deep agents 包含一个可选的 [tool](/oss/langchain/tools) 用于 summarization，让 agents 可以在更合适的时机触发 summarization，例如任务之间，而不是只能按固定 token 间隔触发。

你可以把它追加到 middleware list 中来启用该 tool：

```python
from deepagents import create_deep_agent
from deepagents.backends import StateBackend
from deepagents.middleware.summarization import (
    create_summarization_tool_middleware,
)

backend = StateBackend  # if using default backend

model = "google_genai:gemini-3.5-flash"
agent = create_deep_agent(
    model=model,
    middleware=[  # [!code highlight]
        create_summarization_tool_middleware(model, backend),  # [!code highlight]
    ],  # [!code highlight]
)
```

启用此功能不会禁用默认的“达到模型 context limit 85% 时执行 summarization”的行为。

详情请参阅 @[`SummarizationToolMiddleware`] API reference。

:::

## Context isolation with subagents

Subagents 解决的是 **context bloat problem**。当主 agent 使用会产生大型输出的 tools（web search、file reads、database queries）时，context window 很快会被填满。Subagents 会隔离这些工作：主 agent 只接收最终结果，而不是产生结果的几十个 tool calls。你还可以把每个 subagent 配置得和主 agent 不同（例如 model、tools、system prompt 和 skills）。

**How it works:**

- 主 agent 拥有一个 `task` tool，用于委托工作
- Subagent 使用自己的全新 context 运行
- Subagent 自主执行直到完成
- Subagent 向主 agent 返回一份最终报告
- 主 agent 的 context 保持干净

**Best practices:**

1. **Delegate complex tasks**：对会污染主 agent context 的 multi-step work 使用 subagents。
2. **Keep subagent responses concise**：指示 subagents 返回 summaries，而不是 raw data：

    :::python
    ```python
    research_subagent = {
        "name": "researcher",
        "description": "Conducts research on a topic",
        "system_prompt": """You are a research assistant.
        IMPORTANT: Return only the essential summary (under 500 words).
        Do NOT include raw search results or detailed tool outputs.""",
        "tools": [web_search],
    }
    ```
    :::

    :::js
    ```typescript
    const researchSubagent = {
    name: "researcher",
    description: "Conducts research on a topic",
    systemPrompt: `You are a research assistant.
    IMPORTANT: Return only the essential summary (under 500 words).
    Do NOT include raw search results or detailed tool outputs.`,
    tools: [webSearch],
    };
    ```
    :::

3. **Use the filesystem for large data**：Subagents 可以把结果写入文件；主 agent 只读取它需要的内容。

配置请参阅 [Subagents](/oss/deepagents/subagents)，runtime context propagation 和 per-subagent namespacing 请参阅 [context management](/oss/deepagents/subagents#context-management)。

## Long-term memory

使用默认 filesystem 时，deep agent 会把 working memory files 存在 agent state 中，而它只在单个 thread 内持久存在。
Long-term memory 让 deep agent 能够跨不同 threads 和 conversations 持久化信息。
Deep agents 可以使用 long-term memory 保存用户偏好、累积知识、研究进度，或任何应该超出单个 session 继续存在的信息。

要使用 long-term memory，必须使用 `CompositeBackend`，把特定路径（通常是 `/memories/`）路由到 LangGraph Store，从而提供 durable cross-thread persistence。
`CompositeBackend` 是一种 hybrid storage system：有些文件会无限期持久化，有些文件仍然只属于单个 thread。

:::python
```python
from deepagents import create_deep_agent
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend
from langgraph.store.memory import InMemoryStore

def make_backend(runtime):
    return CompositeBackend(
        default=StateBackend(runtime),
        routes={"/memories/": StoreBackend(runtime)},
    )

agent = create_deep_agent(
    model="google_genai:gemini-3.5-flash",
    store=InMemoryStore(),
    backend=make_backend,
    system_prompt="""When users tell you their preferences, save them to
    /memories/user_preferences.txt so you remember them in future conversations.""",
)
```
:::

:::js
```typescript
import { createDeepAgent, CompositeBackend, StateBackend, StoreBackend } from "deepagents";
import { InMemoryStore } from "@langchain/langgraph-checkpoint";

const agent = await createDeepAgent({
  model: "google_genai:gemini-3.5-flash",
  store: new InMemoryStore(),
  backend: new CompositeBackend(
    new StateBackend(),
    { "/memories/": new StoreBackend() },
  ),
  systemPrompt: `When users tell you their preferences, save them to /memories/user_preferences.txt so you remember them in future conversations.`,
});
```
:::

你不需要预先在 `/memories/` 中放置文件。
你需要提供 backend config、store，以及告诉 agent *保存什么*、*保存在哪里* 的 system prompt instructions。
例如，你可以提示 agent 把偏好存入 `/memories/preferences.txt`。
该路径初始为空；当用户分享值得记住的信息时，agent 会按需使用自己的 filesystem tools（`write_file`、`edit_file`）创建文件。

在 LangSmith 上部署时，如需预置 memories，请使用 [Store API](/langsmith/custom-store)。
设置和 use cases 请参阅 [Long-term memory](/oss/deepagents/memory)。

## Best practices

1. **Start with the right input context** - 对始终相关的约定保持 memory 精简；为 task-specific capabilities 使用聚焦的 skills。
2. **Leverage subagents for heavy work** - 把 multi-step、output-heavy tasks 委托给 subagents，让主 agent 的 context 保持干净。
3. **Adjust subagent outputs in configuration** - 如果调试时发现 subagents 生成了很长的输出，可以在 subagent 的 `system_prompt` 中添加指导，让它生成 summaries 和 synthesized findings。
4. **Use the filesystem** - 把大型输出持久化到文件中（例如 subagent writes 或 [automatic offloading](#offloading)），让 active context 保持较小；模型需要细节时可以用 `read_file` 和 `grep` 拉取片段。
5. **Document long-term memory structure** - 告诉 agent `/memories/` 中有什么，以及应该如何使用它。
6. **Pass runtime context for tools** - 对用户元数据、API keys 和 tools 需要的其他静态配置使用 `context`。
