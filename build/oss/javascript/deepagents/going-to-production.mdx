本指南介绍把 deep agent 从本地 prototype 推向 production deployment 时需要考虑的事项。内容包括如何设定 memory scope、配置 execution environments、添加 guardrails，以及连接 frontend。


## Overview

Agents 会使用 memory 和 execution environment 中的信息来完成任务。
在 production 中，有几个 primitives 决定信息如何共享和访问：

- **Thread**：单次 conversation。默认情况下，message history 和 scratch files 都 scoped 到 thread，不会自动带到其他 thread。
- **User**：与你的 agent 交互的人。Memory 和 files 可以对某个 user 私有，也可以在 users 之间共享。Identity 和 authorization 来自你的 [auth layer](/langsmith/auth)。
- **Assistant**：已配置的 agent instance。Memory 和 files 可以绑定到某个 assistant，也可以在所有 assistants 之间共享。

本页涵盖：
- **[LangSmith Deployments](#langsmith-deployments)**：带 auth、webhooks 和 cron 的 managed infrastructure
- **[Production considerations](#production-considerations)**：invocation、multi-tenancy、authentication、credentials、async 和 durability
- **[Memory](#memory)**：跨 conversations 持久化信息
- **[Execution environment](#execution-environment)**：file storage 和 code execution
- **[Guardrails](#guardrails)**：rate limiting、error handling 和 data privacy
- **[Frontend](#frontend)**：把你的 UI 连接到已部署 agent

## LangSmith Deployments

![Managed Deep Agents packages your agent configuration, tools, and runtime settings for LangSmith](/oss/images/deepagents/production/deepagents-deploy-config.png)

把 Deep Agent 推向 production 的推荐路径是 [Managed Deep Agents](/langsmith/deploy-managed-deep-agent)，这是一个 API-first hosted runtime，用于在 LangSmith 中创建、运行和运营 deep agents。Managed Deep Agents 目前处于 private preview（[加入 waitlist](https://www.langchain.com/langsmith-managed-deep-agents-waitlist)）。对于需要 custom application code、custom routes、advanced authentication 或完整 Agent Server APIs 的团队，也可以直接配置 [LangSmith Deployment](/langsmith/deployment)。两种路径都会 provision agent 所需的基础设施：[threads](/langsmith/use-threads)、[runs](/langsmith/runs)、store 和 checkpointer，因此你不需要自行设置。传统的 LangSmith Deployment 还会开箱即用地提供 [authentication](/langsmith/auth)、[webhooks](/langsmith/use-webhooks)、[cron jobs](/langsmith/cron-jobs) 和 [observability](/langsmith/observability)，并且可以通过 [MCP](/langsmith/server-mcp) 或 [A2A](/langsmith/server-a2a) 暴露你的 agent。

除非另有说明，本页所有 code snippets 都使用以下 `langgraph.json`：



```json langgraph.json
{
  "dependencies": ["."],
  "graphs": {
    "agent": "./src/agent.ts:agent"
  },
  "env": ".env"
}
```


`langgraph.json` 是告诉 LangGraph platform 如何 build 和 run 你的 application 的配置文件。它位于项目 root，并且本地开发（使用 `langgraph dev`）和 production deployment 都需要它。关键字段如下：

| Field | Description |
| --- | --- |
| `dependencies` | 要安装的 packages。`["."]` 会把当前目录作为 package 安装（从 `requirements.txt`、`pyproject.toml` 或 `package.json` 读取）。 |
| `graphs` | 把 graph IDs 映射到代码位置。每个 entry 形如 `"<id>": "./<file>:<variable>"`，其中 `<id>` 是你通过 API invoke graph 时使用的名称，`<variable>` 是从 `<file>` 导出的 compiled graph 或 constructor function。 |
| `env` | 指向包含 environment variables（API keys、secrets）的 `.env` 文件路径。这些变量会在 build time 设置，并在 runtime 可用。 |

完整配置选项（custom Docker steps、store indexing、auth handlers 等）请参阅 [application structure](/oss/javascript/langgraph/application-structure)。

## Production considerations

### Invoking the agent

在 production 中，每次 invocation 都应该携带两个 run-level parameters：

- **`thread_id`**（通过 `config={"configurable": {"thread_id": ...}}` 传入）：conversation 的稳定 identifier。[checkpointer](#durability) 使用它持久化并恢复 message history，因此后续 turns 会延续同一个 conversation。要开始新的 conversation，请生成新的 `thread_id`。
- **`context`**：每次 run 中 tools 和 middleware 在 invocation time 读取的数据，例如 `user_id`、API keys、feature flags 或 session metadata。用 `context_schema` 定义形状，并通过 `runtime.context` 访问。请参阅 [Runtime context](/oss/javascript/deepagents/context-engineering#runtime-context)。

这两者彼此独立，并且几乎总是一起传入：



<DeepagentsProductionInvokeJs />

使用 LangGraph SDK 部署时，SDK 会为你管理 threads，你需要把返回的 `thread_id` 传给每次 run：

```typescript
import { Client } from "@langchain/langgraph-sdk";

const client = new Client({ apiUrl: "<DEPLOYMENT_URL>", apiKey: "<LANGSMITH_API_KEY>" });

const thread = await client.threads.create();
for await (const chunk of client.runs.stream(
  thread.thread_id,  // [!code highlight]
  "agent",
  {
    input: { messages: [{ role: "user", content: "Plan a 3-day trip to Tokyo" }] },
    context: { userId: "user-123" },  // [!code highlight]
    streamMode: "updates",
  },
)) {
  console.log(chunk.data);
}
```


<Tip>
`thread_id` scoped 的是 *conversation*（message history、checkpoints）。`context` 携带的是 tools 和 middleware 读取的 *per-run* data。它们彼此独立：改变其中一个不会影响另一个，你可以传其中任意一个，也可以同时传两个。
</Tip>

### Multi-tenancy

当你的 agent 服务多个 users 时，需要处理三件事：验证每个 user 是谁、控制他们可以访问什么，以及管理 agent 代表他们行动时使用的 credentials。

![Three authentication layers compose: end-user auth, agent-acting-as-user auth, and team RBAC](/oss/images/deepagents/production/auth-layers.png)

#### User identity and access control

[LangSmith Deployments](/langsmith/deployment) 支持 [custom authentication](/langsmith/custom-auth) 来建立 user identity，并支持 [authorization handlers](/langsmith/auth) 控制对 threads、assistants 和 store namespaces 等 resources 的访问。Authorization handlers 在 authentication 成功后运行，可以：

- 给 resources 添加 ownership metadata（例如 `owner: user_id`）
- 返回 filters，让 users 只能看到自己的 resources
- 对 unauthorized operations 返回 HTTP 403 以拒绝访问

分步教程请参阅 [Make conversations private](/langsmith/resource-auth)。演示视频请观看 [custom auth video](https://www.youtube.com/watch?v=DkNqgCz8cjE)。

你如何 [scope memory](#scoping) 和 [execution environments](#execution-environment)，决定 users 之间共享哪些数据。详情见下方 sections。

#### Team access control (RBAC)

LangSmith 的 [role-based access control](/langsmith/rbac) 管理你团队中谁可以 deploy、configure 和 monitor agents。这与上面的 end-user authorization 是分开的。

| Role | Access |
| --- | --- |
| Workspace Admin | 完整权限，包括 settings 和 member management |
| Workspace Editor | 创建和修改 resources，但不能删除 runs 或管理 members |
| Workspace Viewer | Read-only access |

Enterprise plans 支持带细粒度权限的 custom roles。完整 permission model 请参阅 [RBAC reference](/langsmith/rbac)。

#### End-user credentials

当你的 agent 需要代表 user 调用 external APIs 时（例如读取他们的 GitHub repos、发送 Slack messages、查询他们的 data warehouse），你需要一种方式把 user credentials 传给 agent，而不是把它们 hardcode。

**OAuth via Agent Auth.** [Agent Auth](/langsmith/agent-auth) 提供 managed OAuth 2.0 flow。配置 OAuth provider 后，agent 可以请求 scoped 到每个 user 的 tokens。首次使用时，agent 会 [interrupt](/oss/javascript/langgraph/interrupts) execution，并展示 OAuth consent URL。user 完成认证后，agent 会带着有效 token 恢复执行。Tokens 会自动存储和刷新。



```typescript
import { Client } from "@langchain/auth";

const authClient = new Client();

// Inside your agent's tool:
// Access the authenticated user via runtime.serverInfo
const authResult = await authClient.authenticate({
  provider: "github",
  scopes: ["repo", "read:org"],
  userId: runtime.serverInfo.user.identity,  // [!code highlight]
});
// Use authResult.token for GitHub API calls on the user's behalf
```


**Credential injection for sandboxes.** 如果你的 agent 在 [sandbox](#sandboxes) 内运行会调用 external APIs 的代码，[sandbox auth proxy](/langsmith/sandbox-auth-proxy) 可以自动把 credentials 注入 outbound requests，因此 sandbox code 永远不会收到 raw API keys。设置细节请参阅 [Managing secrets](#managing-secrets)。

**Workspace secrets.** 对于所有 users 共享的 API keys（例如组织的 LLM provider keys、search API keys），请把它们作为 [workspace secrets](/langsmith/set-up-hierarchy#configure-workspace-settings) 存储在 LangSmith 中。详情请参阅 [Managing secrets](#managing-secrets)。

### Async

基于 LLM 的 applications 高度 I/O-bound：会调用 language models、databases 和 external services。Async programming 让这些操作可以并发运行，而不是阻塞，从而提高 throughput 和 responsiveness。

<Note>
LangChain 约定在 async method names 前加 `a`（例如 `ainvoke`、`abefore_agent`、`astream`）。Sync 和 async variants 位于同一个 class 或 namespace 中。
</Note>

构建 production 应用时：

- **Create async tools.** LangChain 会把 sync tools 放到单独 thread 中运行，以避免阻塞，但 native async 可以完全避免 threading overhead。
- **Use async middleware methods.** Custom [middleware](/oss/javascript/langchain/middleware/custom) 应实现 async hooks（例如 `abefore_agent`，而不是 `before_agent`）。
- **Use async for external resource lifecycle.** 创建 [sandboxes](#sandboxes) 或连接 [MCP servers](/oss/javascript/langchain/mcp) 涉及 network calls，应当 await。这也是 provision 这些 resources 的 [graph factories](/langsmith/graph-rebuild) 是 async 的原因。

### Durability

Deep Agents 运行在 LangGraph 上，LangGraph 开箱即用提供 [durable execution](/oss/javascript/langgraph/durable-execution)。[persistence](/oss/javascript/langgraph/persistence) layer 会在每一步 checkpoint state，因此当 run 因 failure、timeout 或 [human-in-the-loop](/oss/javascript/langgraph/interrupts) pause 中断时，可以从最后记录的 state 恢复，而无需重新处理之前的 steps。对于会生成许多 subagents 的 long-running deep agents，这意味着 mid-run failure 不会丢失已完成工作。

![Durable execution: when a worker crashes mid-run, another worker picks the run up from the latest checkpoint](/oss/images/deepagents/production/durable-execution.png)

Checkpointing 还支持：

- **Indefinite [interrupts](/oss/javascript/langgraph/interrupts).** Human-in-the-loop workflows 可以暂停几分钟或几天，并从原位置精确恢复。
- **[Time travel](/oss/javascript/langgraph/use-time-travel).** 每个 checkpointed step 都是一个 snapshot，你可以 rewind 到它，从更早 state replay，以便处理出错情况。
- **Safe handling of sensitive operations.** 对于涉及 payments 或其他不可逆 actions 的 workflows，checkpoints 提供 audit trail 和 recovery point，可以检查导致某个 action 的确切 state。

<Tip>
[LangSmith Deployments](/langsmith/deployment) 会自动配置 persistent checkpointer。如果你 self-host，请参阅 [persistence](/oss/javascript/langgraph/persistence) 获取 setup instructions。
</Tip>

## Memory

没有 memory 时，每个 conversation 都会从零开始。Memory 让你的 agent 可以跨 conversations 保留信息（user preferences、learned instructions、past experiences），从而随着时间推移个性化自己的行为。Memory 类型概览请参阅 [memory concepts guide](/oss/javascript/concepts/memory)。

![Short-term memory is scoped to a single thread via checkpoints; long-term memory persists across threads via the store](/oss/images/deepagents/production/memory.png)

### Scoping

Memory 总是跨 conversations 持久存在。核心问题是它在 user 和 assistant boundaries 之间如何 scoped。合适的 scope 取决于谁应该看到和修改这些数据：

| Scope | Namespace | Use case | Example |
| --- | --- | --- | --- |
| **User**（推荐默认） | `(user_id)` | Per-user preferences 和 context | "I prefer concise responses" |
| **Assistant** | `(assistant_id)` | 某个 assistant 的 shared instructions | "Cap posts at 280 characters" |
| **Global** | `(org_id)` | 所有 users 和 assistants 的 read-only policies | "Never disclose internal pricing" |

<Warning>
Shared memory（assistant、user 或 organization scope）是 prompt injection 的载体。如果一个 user 可以写入另一个 user 的 conversation 会读取的 memory，恶意 user 就可能把 instructions 注入 shared state。请在合适场景强制 read-only access。例如，organization-wide policies 应该只能通过 application code 写入，而不是由 agent 自己写入。可以用 [permissions](/oss/javascript/deepagents/permissions) 声明式拒绝对 shared paths 的 writes，或用 [backend policy hooks](/oss/javascript/deepagents/backends#add-policy-hooks) 实现自定义 validation logic。
</Warning>

### Configuration

在 Deep Agents 中，memory 以 files 的形式存储在 virtual filesystem 中。默认情况下，files scoped 到单个 thread（conversation），不会跨 threads 共享。
如果要跨 threads 共享 memory，请把 `/memories/` 这样的 path 路由到会写入 LangGraph [Store](/langsmith/custom-store) 的 [StoreBackend](https://reference.langchain.com/javascript/deepagents/backends/StoreBackend)。使用 [CompositeBackend](https://reference.langchain.com/javascript/deepagents/backends/CompositeBackend) 可以同时给 agent 提供 thread-scoped scratch space 和 cross-thread [long-term memory](/oss/javascript/deepagents/memory)。



<Note>
下面展示的 `rt.serverInfo` 和 `rt.executionInfo` namespace patterns 需要 `deepagents>=1.9.0`。
</Note>


<Tabs>
  <Tab title="User (recommended)">
    按 `user_id` 划分 namespace。每个 user 获得自己的 private memory。这是推荐默认方式，因为大多数 applications 只部署一个 assistant。



```typescript src/agent.ts
import { createDeepAgent, CompositeBackend, StateBackend, StoreBackend } from "deepagents";

export const agent = createDeepAgent({
  backend: new CompositeBackend(
    new StateBackend(),
    {
      "/memories/": new StoreBackend({
        namespace: (rt) => [
          rt.serverInfo.assistantId,  // [!code highlight]
          rt.serverInfo.user.identity,  // [!code highlight]
        ],
      }),
    },
  ),
  systemPrompt: `You have persistent memory at /memories/.

  Read /memories/instructions.txt at the start of each conversation for
  accumulated knowledge and preferences. When you learn something that
  should persist, update that file.`,
});
```

    按 `assistant_id` 划分 namespace。Memory 会在同一 assistant 的所有 users 之间共享，因此任何 user 都可以读取或更新它。适合对使用该 assistant 的所有人都生效的 shared instructions 或 knowledge（例如 "always reply in formal tone"）。


## Execution environment

在本地，agents 可以直接读写磁盘文件并运行 shell commands。在 production 中，你需要考虑 isolation 和 persistence。正确设置取决于你的 agent 是否需要执行代码：

- **Filesystem backends**：如果 agent 只读写 files，这就足够了。根据 persistence 需求选择 backend：thread-scoped scratch space、cross-thread storage，或两者混合。
- **Sandboxes**：添加带 `execute` tool 的 isolated container，用于运行 shell commands。如果 agent 需要运行代码、安装 packages，或执行超出 file I/O 的操作，请使用 sandbox。

### Filesystem

根据哪些内容需要持久化选择 backend：

- [StateBackend](https://reference.langchain.com/javascript/deepagents/backends/StateBackend)（默认）：thread-scoped scratch space。Files 会通过 checkpointer 在同一 thread 的 turns 之间持久存在，但不会跨 threads 共享。每一步都会 checkpoint，因此应避免写入 large files。
- [StoreBackend](https://reference.langchain.com/javascript/deepagents/backends/StoreBackend)：跨 conversations 存活的 cross-thread storage。使用 [namespace factory](/oss/javascript/deepagents/backends#namespace-factories) 设定 scope。
- [CompositeBackend](https://reference.langchain.com/javascript/deepagents/backends/CompositeBackend)：两者混合。默认 thread-scoped scratch space，同时为 `/memories/` 等特定 paths 配置 cross-thread routes。



完整 backends 列表及 custom backend 构建方法，请参阅 [backends](/oss/javascript/deepagents/backends)。

<Warning>
`FilesystemBackend` 和 `LocalShellBackend` 会直接访问 host。不要在 deployed agents 中使用它们。
</Warning>

### Sandboxes

如果你的 agent 需要运行代码（不只是读写 files），请使用 [sandbox](/oss/javascript/deepagents/sandboxes)。Sandboxes 同时提供 filesystem 和用于运行 shell commands 的 `execute` tool，且全部在 isolated container 内运行。这种 isolation 也会保护你的 host：如果 agent 的代码耗尽 memory 或 crash，只有 sandbox 受影响。你的 server 会继续运行。

#### Lifecycle

关键决策是 sandbox 存活多久。每个 conversation 都获得一个新的 sandbox，还是多个 conversations 共享一个 persistent environment？

| Scope | Sandbox ID stored on | Lifecycle | Example use case |
|---|---|---|---|
| **Thread-scoped** | [Thread](/langsmith/use-threads) metadata | 每个 conversation 新建，TTL 到期后清理 | 每个 conversation 都应干净开始的数据分析 bot |
| **Assistant-scoped** | [Assistant](/langsmith/assistants) config | 所有 conversations 共享 | 跨 conversations 维护 cloned repo 的 coding assistant |

<Note>
下面的示例使用 async [graph factory](/langsmith/graph-rebuild)，而不是 static graph，因为 sandbox 需要 `thread_id` 或 `assistant_id` 来查找或创建正确的 sandbox。Graph factories 不会接收完整 `Runtime`（没有 `server_info` 或 `execution_info`）；相反，它们接收 `RunnableConfig`，并从 `config["configurable"]` 读取 `thread_id` 和 `assistant_id`。factory 是 async，因为 sandbox 创建是 I/O-bound 操作，并且需要 invocation time 才可用的 per-run information。
</Note>

    每个 conversation 都获得自己的 sandbox。[graph factory](/langsmith/graph-rebuild) 从 run config 读取 `thread_id`，因此每个 [thread](/langsmith/use-threads) 自动获得自己的 isolated environment。provider 的 label-based lookup 会处理跨 runs 的 deduplication。sandbox [TTL](/langsmith/configure-ttl) 到期后会被清理。

    所有 conversations 共享一个 sandbox。[graph factory](/langsmith/graph-rebuild) 从 `config["configurable"]` 读取 [assistant](/langsmith/assistants) ID，因此同一 assistant 上的每个 thread 都会回到同一个 environment。Files、installed packages 和 cloned repositories 会跨 conversations 保留。

        Assistant-scoped sandboxes 会随着时间积累 files、installed packages 和其他 in-sandbox state。请用你的 sandbox provider 配置 TTL、使用 snapshots 定期重置，或实现 cleanup logic，防止 sandbox 的 disk 和 memory 无限制增长。

因为 `agent` 变量是 async function（不是 compiled graph），server 会把它视为 [graph factory](/langsmith/graph-rebuild)，并在每次 run 时调用它、注入 config。factory 会通过 provider 的 label-based search 查找或创建 sandbox，并返回连接到该 sandbox 的新 agent graph。

使用 `langgraph deploy` 部署后，请从 application code 使用 SDK invoke agent。无论 scope 如何，client-side code 都相同。scoping 完全由上面的 agent factory 处理，但行为不同：

<Tabs>
  <Tab title="Thread-scoped">
    每个 thread 都获得自己的 sandbox。同一 thread 内的 follow-up messages 会复用同一个 sandbox，但新的 thread 总是从干净环境开始，不带 previous conversations 的 leftover files 或 installed packages。



```typescript client.ts
import { Client } from "@langchain/langgraph-sdk";

const client = new Client({ apiUrl: "<DEPLOYMENT_URL>", apiKey: "<LANGSMITH_API_KEY>" });

// Conversation 1: install pandas and analyze data
const thread1 = await client.threads.create();
for await (const chunk of client.runs.stream(
  thread1.thread_id,
  "agent",
  { input: { messages: [{ role: "human", content: "Install pandas and analyze sales_data.csv" }] } },
)) {
  console.log(chunk.data);
}

// Follow-up in the same conversation -> pandas is still installed
for await (const chunk of client.runs.stream(
  thread1.thread_id,
  "agent",
  { input: { messages: [{ role: "human", content: "Now plot the results" }] } },
)) {
  console.log(chunk.data);
}

// Conversation 2: fresh sandbox -> pandas is NOT installed, no files from conversation 1
const thread2 = await client.threads.create();
for await (const chunk of client.runs.stream(
  thread2.thread_id,
  "agent",
  { input: { messages: [{ role: "human", content: "What packages are installed?" }] } },
)) {
  console.log(chunk.data);
}
```


  </Tab>
  <Tab title="Assistant-scoped">
    所有 threads 共享一个 sandbox。当 sandbox 中存在重建成本很高的 state 时，这很有用，例如 cloned repo、installed dependencies 或 build artifacts。同一 assistant 上的任何 conversation 都会从上一次离开的地方继续，无需重复 setup。



```typescript client.ts
import { Client } from "@langchain/langgraph-sdk";

const client = new Client({ apiUrl: "<DEPLOYMENT_URL>", apiKey: "<LANGSMITH_API_KEY>" });

// Conversation 1: clone and set up the project
const thread1 = await client.threads.create();
for await (const chunk of client.runs.stream(
  thread1.thread_id,
  "agent",
  { input: { messages: [{ role: "human", content: "Clone https://github.com/org/repo and install dependencies" }] } },
)) {
  console.log(chunk.data);
}

// Conversation 2: repo and dependencies are still there
const thread2 = await client.threads.create();
for await (const chunk of client.runs.stream(
  thread2.thread_id,
  "agent",
  { input: { messages: [{ role: "human", content: "Run the test suite and fix any failures" }] } },
)) {
  console.log(chunk.data);
}
```


  </Tab>
</Tabs>

#### File transfers

Sandboxes 是 isolated containers，因此你的 application code 无法直接访问其中的 files。使用 `upload_files()` 和 `download_files()` 在 sandbox boundary 之间移动数据：

- **Seed the sandbox before the agent runs**：上传 user files、[skill](/oss/javascript/deepagents/skills) scripts、configuration 或 [persistent memories](/oss/javascript/deepagents/memory)，让 agent 从一开始就拥有所需内容
- **Retrieve results after the agent finishes**：下载生成的 artifacts（reports、plots、exports），并把更新后的 memories 同步回来，供 future conversations 使用

provider-specific file transfer 示例请参阅 [working with files](/oss/javascript/deepagents/sandboxes#working-with-files)。provider setup、security 和 lifecycle patterns 请参阅完整 [sandboxes guide](/oss/javascript/deepagents/sandboxes)。

<Accordion title="Example: syncing skills and memories with custom middleware">
  agent 需要执行的 [Skill](/oss/javascript/deepagents/skills) scripts 必须在 agent 运行前上传到 sandbox。你可能也希望同步 [memories](/oss/javascript/deepagents/memory)，让 agent 可以在 container 内读取和更新它们。使用带 `before_agent` 和 `after_agent` hooks 的 [custom middleware](/oss/javascript/langchain/middleware/custom)，在 sandbox boundary 之间移动 files：



```typescript src/agent.ts
import { createMiddleware } from "langchain";
import { createDeepAgent, CompositeBackend, StoreBackend } from "deepagents";
import { DaytonaSandbox } from "@langchain/daytona";

function safeFilename(key: string): string {
  const name = key.split("/").pop()!;
  if (name.includes("..") || /[*?]/.test(name)) {
    throw new Error(`Invalid key: ${key}`);
  }
  return name;
}

const createSandboxSyncMiddleware = (backend: CompositeBackend) => {
  return createMiddleware({
    name: "SandboxSyncMiddleware",
    beforeAgent: async (state, runtime) => {
      // Upload skill scripts and memories into the sandbox
      const userId = runtime.serverInfo.user.identity;  // [!code highlight]
      const store = runtime.store;
      const encoder = new TextEncoder();
      const files: [string, Uint8Array][] = [];
      for (const item of await store.search(["skills", userId])) {
        const name = safeFilename(item.key);
        files.push([`/skills/${name}`, encoder.encode(item.value.content)]);
      }
      for (const item of await store.search(["memories", userId])) {
        const name = safeFilename(item.key);
        files.push([`/memories/${name}`, encoder.encode(item.value.content)]);
      }
      if (files.length > 0) {
        await backend.uploadFiles(files);
      }
    },
    afterAgent: async (state, runtime) => {
      // Sync updated memories back to the store
      const userId = runtime.serverInfo.user.identity;  // [!code highlight]
      const store = runtime.store;
      const items = await store.search(["memories", userId]);
      const results = await backend.downloadFiles(
        items.map((item) => `/memories/${item.key}`),
      );
      const decoder = new TextDecoder();
      for (const result of results) {
        if (result.content) {
          await store.put(
            ["memories", userId],
            result.path.split("/").pop()!,
            { content: decoder.decode(result.content) },
          );
        }
      }
    },
  });
};

const backend = new CompositeBackend(
  await DaytonaSandbox.fromId(sandbox.id),
  {
    "/skills/": new StoreBackend({
      namespace: (rt) => ["skills", rt.serverInfo.user.identity],  // [!code highlight]
    }),
    "/memories/": new StoreBackend({
      namespace: (rt) => ["memories", rt.serverInfo.user.identity],  // [!code highlight]
    }),
  },
);

export const agent = createDeepAgent({
  backend,
  middleware: [createSandboxSyncMiddleware(backend)],
});
```


</Accordion>

#### Managing secrets

Sandboxes 是 isolated containers，因此 host 中的 environment variables 在其中不可用。有两种方式可以向 sandbox code 提供 API keys 和其他 secrets：

**Auth proxy（推荐）。** [sandbox auth proxy](/langsmith/sandbox-auth-proxy) 会拦截 sandbox 发出的 outbound requests，并自动注入 authentication headers。Sandbox code 像平常一样调用 external APIs，proxy 会根据 destination host 添加正确 credentials。这意味着 API keys 永远不会出现在 sandbox code、environment variables 或 logs 中。

![The sandbox auth proxy injects credentials into outbound requests so secrets never enter the sandbox](/oss/images/deepagents/production/sandbox-auth-proxy.png)

```json
{
  "proxy_config": {
    "rules": [
      {
        "name": "openai-api",
        "match_hosts": ["api.openai.com"],
        "inject_headers": {
          "Authorization": "Bearer ${OPENAI_API_KEY}"
        }
      },
      {
        "name": "anthropic-api",
        "match_hosts": ["api.anthropic.com"],
        "inject_headers": {
          "x-api-key": "${ANTHROPIC_API_KEY}"
        }
      }
    ]
  }
}
```

`${SECRET_KEY}` references 会解析为存储在 LangSmith [workspace settings](/langsmith/set-up-hierarchy#configure-workspace-settings) 中的 secrets。创建引用这些 secrets 的 template 前，请先在那里配置 secrets。

**Workspace secrets.** 对于不需要 proxy-based injection 的 API keys（例如 agent server 自身使用的 keys，而不是 sandbox code 使用的 keys），请把它们作为 [workspace secrets](/langsmith/set-up-hierarchy#configure-workspace-settings) 存储在 LangSmith 中。它们会在 runtime 作为 environment variables 对 workspace 中的所有 agents 可用。

<Warning>
避免通过 environment variables 或 file uploads 把 secrets 传入 sandboxes。Agents 可以读取 sandbox 内任何可访问 file 或 environment variable，包括 credentials。auth proxy 会让 secrets 完全留在 sandbox 外。
</Warning>

## Guardrails

Production 中的 agents 会自主运行，这意味着它们可能无限循环、触发 rate limits，或处理包含敏感信息的 user data。Deep Agents 提供两层保护：

- **[Permissions](/oss/javascript/deepagents/permissions)**：声明式 allow/deny rules，用于控制 agent 可以 read 或 write 哪些 files 和 directories。使用 permissions 可以把 agent 隔离到 working directory、保护 sensitive files，或强制 read-only memory。
- **[Middleware](/oss/javascript/langchain/middleware/built-in)**：包裹 model 和 tool calls 的 hooks，用于 rate limiting、error handling 和 data privacy。

![Middleware hooks - before_model, wrap_model_call, wrap_tool_call, after_model - wrap the agent loop so policies run deterministically around every relevant step](/oss/images/deepagents/production/middleware-lifecycle.png)

### Rate limiting

这里的 rate limiting 指的是限制 agent 在一次 run 内自己的 LLM 和 tool 使用量，而不是 incoming requests 的 API gateway rate limiting。

如果没有限制，困惑的 agent 可能通过反复调用同一个 tool 或进行数百次 model calls，在几分钟内耗尽你的 LLM API budget。请为每次 run 设置 model calls 和 tool executions 的上限：



```typescript
import { createAgent, modelCallLimitMiddleware, toolCallLimitMiddleware } from "langchain";

const agent = createAgent({
  model: "google_genai:gemini-3.5-flash",
  middleware: [
    modelCallLimitMiddleware({ runLimit: 50 }),
    toolCallLimitMiddleware({ runLimit: 200 }),
  ],
});
```


使用 `run_limit` 限制单次 invocation 内的 calls（每个 turn 重置）。使用 `thread_limit` 限制整个 conversation 内的 calls（需要 checkpointer）。完整配置请参阅 [ModelCallLimitMiddleware](https://reference.langchain.com/javascript/langchain/index/modelCallLimitMiddleware) 和 [ToolCallLimitMiddleware](https://reference.langchain.com/javascript/langchain/index/toolCallLimitMiddleware)。

### Handling errors

并非所有 errors 都应该用同一种方式处理。Transient failures（network timeouts、rate limits）应自动 retry。LLM 可以自行恢复的 errors（bad tool output、parsing failures）应反馈给模型。需要 human input 的 errors 应暂停 agent。带代码示例的完整拆解请参阅 [Handle errors appropriately](/oss/javascript/langgraph/thinking-in-langgraph#handle-errors-appropriately)。

Middleware 负责处理 transient case。Model calls 和 tool calls 各自都有带 exponential backoff 的 retry middleware。如果 primary model provider 完全不可用，fallback middleware 会切换到替代模型：



```typescript
import {
  createAgent,
  modelFallbackMiddleware,
  modelRetryMiddleware,
  toolRetryMiddleware,
} from "langchain";

const agent = createAgent({
  model: "google_genai:gemini-3.5-flash",
  middleware: [
    // Retry model calls on rate limits, timeouts, and 5xx errors
    modelRetryMiddleware({ maxRetries: 3, backoffFactor: 2.0, initialDelayMs: 1000 }),
    // If the primary model is fully down, fall back to an alternative
    modelFallbackMiddleware("gpt-5.4"),
    // Retry specific tools that hit external APIs (not all tools)
    toolRetryMiddleware({
      maxRetries: 2,
      tools: ["search", "fetch_url"],
      retryOn: [TimeoutError, TypeError],
    }),
  ],
});
```


请把 [ToolRetryMiddleware](https://reference.langchain.com/javascript/langchain/index/toolRetryMiddleware) scope 到特定 tools，而不是 retry 一切。失败的 filesystem `read_file` 通常不会因为 retry 受益，但 timeout 的 web search 很可能会。完整配置请参阅 [ModelRetryMiddleware](https://reference.langchain.com/javascript/langchain/index/modelRetryMiddleware) 和 [ModelFallbackMiddleware](https://reference.langchain.com/javascript/langchain/index/modelFallbackMiddleware)。

### Data privacy

如果你的 agent 会处理可能包含 emails、credit card numbers 或其他 PII 的 user input，你可以在其到达 model 或存入 logs 之前检测并处理：



```typescript
import { createAgent, piiMiddleware } from "langchain";

const agent = createAgent({
  model: "google_genai:gemini-3.5-flash",
  middleware: [
    piiMiddleware("email", { strategy: "redact", applyToInput: true }),
    piiMiddleware("credit_card", { strategy: "mask", applyToInput: true }),
  ],
});
```


Strategies 包括 `redact`（替换为 `[REDACTED_EMAIL]`）、`mask`（局部遮罩，例如 `****-****-****-1234`）、`hash`（deterministic hash）和 `block`（raise error）。你也可以为 domain-specific patterns 编写 custom detectors。

完整配置请参阅 [piiMiddleware](https://reference.langchain.com/javascript/langchain/index/piiMiddleware)。


完整可用 middleware 列表请参阅 [prebuilt middleware](/oss/javascript/langchain/middleware/built-in)。

## Frontend

Deep Agents 使用 [`useStream`](/oss/javascript/langchain/frontend/overview) 把 UI 连接到 agent backend。`useStream` 是 frontend hook（支持 React、Vue、Svelte 和 Angular），可以实时 stream messages、subagent progress 和来自 agent 的 custom state。

本地开发时，`useStream` 指向 `http://localhost:2024`。在 production 中，请指向你的 [LangSmith Deployment](/langsmith/deployment)，并配置 reconnection，避免用户连接断开时丢失进度。

```tsx
import { useStream } from "@langchain/react";

function App() {
  const stream = useStream<typeof agent>({
    apiUrl: "https://your-deployment.langsmith.dev",
    assistantId: "agent",
    reconnectOnMount: true,    // Resume stream after page refresh or navigation
    fetchStateHistory: true,   // Load full thread history on mount
  });
}
```

`reconnectOnMount` 会自动接上 in-progress run。如果 user 在 agent 工作时刷新页面，他们会看到它继续运行，而不是空白页面。`fetchStateHistory` 会加载该 thread 的完整 conversation history，因此 returning users 能看到之前的 messages。

对于会生成许多 subagents 的 deep agent workflows，在 submit 时设置较高的 `recursionLimit`，避免 long-running executions 被提前截断：

```tsx
stream.submit(
  { messages: [{ type: "human", content: text }] },
  {
    streamSubgraphs: true,
    config: { recursionLimit: 10000 },
  },
);
```

Deep Agents 专属 UI patterns，例如 subagent cards、todo lists 和 custom state rendering，请参阅 [frontend guide](/oss/javascript/deepagents/frontend/overview)。
